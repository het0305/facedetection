1Project at a glance

ItemDetail
TitleFaceAttend: Face Recognition Attendance System with Anti-Spoofing
TypeFull-stack web application (React + Node.js/Express + MongoDB) with AI face models
ProblemManual roll-call is slow, error-prone and allows proxy attendance. Simple face systems can be fooled by a photo and may mark the wrong person.
SolutionA kiosk camera recognises each person's face, checks they are a real live person, and marks attendance once per day. An admin console manages users and reports.
Key ideaPre-trained deep-learning models (transfer learning) turn each face into 128 numbers; faces are compared by distance.
Top priorityNever mark the wrong person. If unsure, show "Unable to verify identity".

Objectives

  1. Mark attendance automatically and contactlessly using face recognition.
  2. Prevent proxy attendance with anti-spoofing (photo, video and screen attacks).
  3. Avoid false matches with strict thresholds, a margin check and multi-frame confirmation.
  4. Allow only one attendance record per person per day.
  5. Protect biometric data with encryption and secure admin login.
  6. Give the admin a dashboard, a searchable attendance list and Excel export.

Main features

  • Guided 5-pose face registration with automatic capture
  • Duplicate-face detection at registration
  • Kiosk scanning with live on-screen hints
  • Passive liveness (2 models) + head-turn challenge
  • Present / Late status by time zone
  • Dashboard: present, late and absent today, last 7 days
  • Attendance filters, status edit, delete, Excel export
  • Kiosk device activation and deactivation
  • Audit log of every important action
  • Encrypted face templates, no photos stored

6Registration workflow

  1. Admin signs in and opens Register user.
  2. Enters details: name and roll number (the roll number must be unique).
  3. Captures 5 poses: front, slight left, slight right, slight up and slight down. Each pose is captured automatically after 2 good frames.
  4. Each photo is checked on the server (/students/check-sample): exactly one face, big enough, sharp, well lit, correct pose, and a real person (liveness).
  5. Descriptors are created: the ResNet model turns each face into 128 numbers.
  6. Duplicate check: if the face matches an existing user (distance < 0.42), the admin is warned.
  7. Encrypt and save: the 5 descriptors are encrypted with AES-256-GCM and saved. The photos are discarded.
  8. Gallery updated: the new user can scan at the kiosk right away. No training is needed.
Viva point: registration does not train the model. It only stores the face numbers.

7Attendance (kiosk) workflow

Camera frame→Detect face→Landmarks→Quality check→Passive liveness→Descriptor→Match→Head-turn challenge→Confirm→Mark
PhaseWhat happensKiosk shows
SEARCHEach frame: find the face, check quality, check passive liveness (≥ 0.6), create the descriptor and match it. The same person must be matched on 3 frames (5 if the match is weaker)."Look at the camera", "Move closer to the camera"…
CHALLENGEA random task: turn the head slightly left or right within 10 seconds. The same face must stay in view."Please turn your head slightly to your left."
CONFIRMOne more front-facing frame must match the same person."Look straight at the camera"
DONEAttendance is saved once per day (Present or Late), with distance, confidence and liveness score."Attendance marked ✓" / "Already marked today"
Possible results
  • MARKED: new record saved
  • ALREADY_MARKED: already present today
  • UNVERIFIED: not sure who it is, so nothing is marked
  • Liveness / challenge failed: possible spoof, recorded in the audit log
Why so many steps?
  • Multiple frames remove one-off wrong matches.
  • The challenge defeats photos and still screens.
  • The confirm step ensures it is the same person after the turn.

8AI models & transfer learning

Transfer learning means reusing a model already trained on a huge dataset for a new task instead of training from zero. This project uses the feature extraction type: the models are frozen (not retrained) and only their outputs are used. No training or fine-tuning is done.
#ModelJob (nickname)Input → OutputRuns in
1SSD MobileNet v1Face detection (Finder)Camera image → face box + scorefaceEngine.js
2Face Landmark 6868 face points (Pointer)Face crop → 68 (x, y) pointsfaceEngine.js, faceGeometry.js
3Face Recognition ResNetFace descriptor (Fingerprinter)Aligned 150×150 face → 128 numbersfaceEngine.js → matcher.js
4MiniFASNetV2Anti-spoof (Guard 1)80×80 crop (2.7× face) → real scoreliveness.js
5MiniFASNetV1SEAnti-spoof (Guard 2)80×80 crop (4.0× face) → real scoreliveness.js
How each model is built (simple)
  • SSD = Single Shot Detector: finds objects in one pass. MobileNet = a light, fast CNN.
  • ResNet = Residual Network: a deep CNN with "skip connections" that make deep networks train well.
  • MiniFASNet = a small CNN for Face Anti-Spoofing; "SE" adds a Squeeze-and-Excitation attention block.
Where the model files come from
  • Models 1–3: the @vladmandic/face-api package (npm run models copies them into backend/models).
  • Models 4–5: ONNX files from the open-source face-anti-spoofing project (Apache-2.0), checked with SHA-256.
  • All are loaded once at server start.
Remember the order: Find → Point → Guard → Fingerprint (detection → landmarks → anti-spoof → recognition).

9Face matching algorithm

Every face becomes a vector of 128 numbers. Two faces are compared using the Euclidean distance:

d(A, B) = √( (a₁ − b₁)² + (a₂ − b₂)² + … + (a₁₂₈ − b₁₂₈)² )

A small distance means the same person, and a large distance means different people. Each user has 5 stored samples; the distance to a user is the smallest distance to any of their samples (strategy min).

#Rule (matcher.js + scanSession.js)Value
1Best distance must be within the threshold≤ 0.5
2The second-best different person must be at least this much further away (margin)≥ 0.06
3The same person must be matched on consecutive good frames3 frames (5 if median distance > 0.4)
4Confidence label stored with the recordhigh if ≤ 0.4, else standard
5Otherwise the result is "unknown" (NO_MATCH or AMBIGUOUS)"Unable to verify identity"
Why distance and not a classifier? A classifier must be retrained whenever a new person joins. Distance-based comparison works for any number of people, and a new user only needs to be registered.

10Anti-spoofing (liveness)

1. Passive liveness (no action needed)
  • Two MiniFASNet models look at the face at two zoom levels (2.7× and 4.0×).
  • Each outputs probabilities (softmax); class 1 = "real".
  • The two "real" scores are averaged: score ≥ 0.6 passes.
  • Detects print photos, phone and laptop screens, and replayed videos from texture, moiré and edge clues.
2. Active challenge (user action)
  • A random instruction: turn the head slightly left or right.
  • Head angle (yaw) is measured from the 68 landmarks; it must change by ≥ 0.15.
  • Must be done within 10 seconds, with the same face kept in view.
  • Blink detection is also available (eye aspect ratio), off by default.
Why both? A passive model alone can be fooled by a very good print; a challenge alone can be fooled by a video. Together they are much stronger. Every failure is saved in the audit log as a security event.

16Demo script for the viva (about 5 minutes)

  1. Start both servers before the viva and open http://localhost:3000. Explain the two sides: kiosk and admin console.
  2. Sign in as admin (het) → show the Dashboard: active users, present, late, absent, last 7 days.
  3. Register a user → show the 5-pose capture, quality hints and automatic capture. Say: "Photos are not stored; only encrypted 128-number descriptors."
  4. Open the kiosk (/kiosk) → look at the camera → follow the head-turn instruction → "Attendance marked ✓".
  5. Scan again → "Already marked today" (one record per day).
  6. Show a photo on a phone to the kiosk → it is rejected (liveness / challenge failed).
  7. Attendance page → show the new record with its verification details → click Export Excel.
  8. Settings → Audit log → show the login, registration and spoof attempt records.
Before the viva: check that MongoDB is running, the camera works in the browser, the room has good front lighting, and at least one user is registered. Keep a phone photo ready for the spoof demo.

18Advantages, limitations, future scope

Advantages
  • Fast and contactless
  • Stops proxy attendance
  • No wrong-person marks by design
  • No model training needed
  • Add users any time
  • Encrypted biometric data
  • Runs on a normal PC, no GPU
  • Excel reports and audit trail
Limitations
  • Needs good lighting
  • Identical twins can be confused
  • High-quality 3D masks may pass
  • Large changes (heavy beard, mask) may need re-registration
  • Needs a camera at each kiosk
  • Thresholds should be tuned on local data
Future scope
  • Cloud deployment with HTTPS
  • Mobile app
  • SMS / email alerts to parents
  • Classes, subjects, timetables
  • Depth / infrared camera liveness
  • GPU backend for many kiosks
  • Mask-aware recognition

60-second answer: "Explain your project."
"My project is a face recognition attendance system built on the MERN stack: React, Node.js with Express, and MongoDB. A kiosk camera sends frames to the server, where five pre-trained models are used through transfer learning, as feature extraction. SSD MobileNet finds the face, Face Landmark 68 marks 68 points, two MiniFASNet models check that the face is real, and a ResNet model turns the face into 128 numbers. These are compared with stored faces using Euclidean distance with a 0.5 threshold, a margin check and three stable frames, followed by a head-turn challenge, so a photo cannot be used and the wrong person is never marked. Attendance is saved once per day. Face data is encrypted with AES-256, and the admin can manage users, view a dashboard and export attendance to Excel."
